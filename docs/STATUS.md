# Status

## Built

- PWA with conversational logging, duplicate guard, handoff brief, Ask box, voice input, smart rhythm predictions & advice (`src/domain/predictions.ts`), and on-device smart notifications (nap wind-down, nap sweet-spot, expected wake-up, upcoming feed, and diaper check).
- Capacitor Android and iOS projects generated (`android/` and `ios/`, synced with `npm run cap:sync`); CI builds `calendaby-debug-apk`.
- Hybrid capture: the rules parser handles what it can on the phone; leftovers go to the agent.
- `backend/`: Hono routes on SQLite (`node:sqlite`), one POST route per operationId (`recordEvents`, `listEvents`).
- `agent/agent.ts`: capture and chat modes. `listEvents` and `getPredictions` (deduced sleep, feed, diaper, and 7-day trend insights) are tools available to the chat agent. Each agent call first syncs the app's events into the backend.
- Model from `MODEL_NAME`: OpenRouter, default `openai/gpt-6-luna`.
- Clerk sign-in is required when `VITE_CLERK_PUBLISHABLE_KEY` is set (`src/ui/AuthGate.tsx`); without the key the app runs signed out. The caregiver name defaults to the account's first name, and "Continue without signing in" appears if Clerk can't load (offline). With `CLERK_SECRET_KEY` set, `/api/agent` and `/api/backend/*` require a Clerk session token (401 otherwise); without it the API stays open as before. Logging works signed out. Calendar tab: Sync Gmail, confirm or dismiss proposals, and a two-week agenda (confirmed visits plus Google Calendar) that flags clashes with the predicted nap or feed. The app also reads Gmail by itself when it opens or returns to the front (at most every 30 minutes) and sends a notification when a new appointment is found (`src/domain/newProposals.ts`; needs Smart Reminders on and notification permission; only while the app is open, there is no server push). Each appointment has a "What to expect" section (`src/domain/visitPrep.ts`): the checkup for the baby's age on the visit day with its vaccines and the fever advice, each cited (CDC, MedlinePlus), plus a plan from the baby's own log (leave time, when to feed, what to pack); nothing there is written by the model. Confirmed visits are cached on the device and schedule reminders (day before, 2 hours before, time to leave) when reminders are on. Backend Gmail appointment import is built (`importAppointments`, `listAppointments`, `setAppointmentStatus`; proposals only, the parent confirms). See `docs/PLAN_CLERK.md`.
- Feature switches: the `features` table in the on-device SQLite (schema v2) holds each feature's label, group, order and on/off state; Profile lists them from the database and Today, the tabs and the Ask buttons follow them. A feature the table does not know counts as on. Entries can be edited from the Timeline (time, amounts, type, notes; sleep start and end); edits keep the original id and who logged it.
- Activities and pumping (from `docs/ANALYSIS_HUCKLEBERRY.md`): two event kinds, `activity` (`type` is an id from the on-device `activity_types` table, seeded with tummy, bath, outdoor, indoor; schema v3; custom types can be added from the Tummy & Play tab) and `pump` (amount, side, minutes; never counted as a feed). Typed or spoken ("tummy time 5 min", "pumped 4 oz left"), Logger tabs, Timeline "Activities" filter, edit sheet, Today tiles for tummy minutes and pumped milk (shown once there is data), handoff lines, and the agent's `record_events` tool. Feature switches `activities` and `pumping`.
- Activity tab (`src/ui/Activity.tsx`, behind the `activities` switch): tummy time against a daily goal the parent sets (setting `tummyGoal`, default 30 min, not medical advice), one-tap 3/5/10 minute logging for every activity type, a 7-day active-minutes chart, today's minutes per type and recent sessions with edit. Types now also include crawling, walking and swimming (schema v4 adds them to existing installs). The nav grows to six items when it is on.
- Appearance (Profile > Look & feel, Sections): one validated `theme` setting in the on-device SQLite (`src/domain/theme.ts`, falls back to the shipped look if unreadable). Page-wide: mode (auto/light/night), main colour (swatches or any colour), corners, spacing, size, font, shadows. Per section (top bar, status pill, next nap, quick buttons, say-it box, last cards, totals, advice, handoff, bottom bar): own colour, fill (tint/solid/outline) and corners. Sections opt in with `useSection(id)` (`src/ui/themeContext.ts`); colours derive from one `--accent` in `src/index.css`. Sleep and diaper greens stay fixed because they carry meaning.
- Family sharing (`docs/PLAN_SHARING.md`): signed-in caregivers, each with their own Google account, join one household with an invite code (Profile > Family) and see the same log. Each phone keeps its own SQLite plus an outbox (schema v6, `sync_pending`); `src/domain/sync.ts` pushes unsent changes and pulls new ones by change number, on every local change, on app focus, when back online and every 30 seconds (`src/ui/useSync.ts`). Server: `backend/household.ts` (Turso/libSQL; `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`) and `backend/sharing.ts`. Sign-in is required whenever Clerk is configured; guest mode is removed. Each phone records whether an entry came from another caregiver (`events.remote`, schema v10); when a phone moves to a different family, or is removed from one, it drops the entries other caregivers made there and sends only its own into the new one (phones that upgrade count their existing entries as their own, since their origin was never recorded). Accepting an invite code always moves the person into that family as a member, even from a family with other people; if they owned the one they leave, its longest-standing member becomes owner, and codes still work after a phone swaps the hyphen for another dash or a space (`backend/household.ts`). "Invite someone" opens the share sheet with the code and where to type it (`src/share.ts`: `@capacitor/share` in the phone app, the Web Share API in the browser, the clipboard otherwise; the handoff and summary buttons use it too). Tested through the real routes with two phone databases (`backend/sync.test.ts`); not yet tried on two real phones.
- Data-driven options (rule 9): the quick-pick lists (feed and diaper tags, medicines, bottle amounts in oz and mL, durations, activity minutes, colour swatches) live in the on-device `option_list` table (schema v8) and the starting values of the sleep goal, tummy goal, units, baby name and briefing time are seeded into `settings`; seeds never overwrite a stored choice. Profile > Quick picks & goals edits them (add, remove, restore the originals); `store.options()` and `store.setting()` read from memory so screens render without waiting. Lists stay on the phone, not shared. Starting data is planted by versioned seeds (`src/domain/seeds.ts`, table `seed_applied`, schema v9); see ARCHITECTURE.md > Seeds. Still in code, planned next: night hours, nap wind-down lead, duplicate window, visit lead time, and the pediatric reference content (see Known gaps).
- The browser version asks the browser to keep its saved data (`src/keepStorage.ts`, called from `src/pwa.ts`), so the log is less likely to be cleared when space runs low or the app goes unused; the browser may refuse, and signed-in logs are also on the server. Firefox may show a permission prompt for it.
- Install and updates (browser): the manifest has an `id`, narrow and wide screenshots (`npm run screenshots` retakes them from the signed-out app into `public/screenshots/`, kept out of the offline cache) and a `web+calendaby:` protocol handler. A new version waits until the app is in the background before it applies (`src/updateWhenAway.ts`), so the page never reloads mid-entry.
- Invite links: the invite message carries `https://calendaby.vercel.app/?join=CODE`; opening it, or a `web+calendaby:join/CODE` link, lands on Profile with the code in the join box (`src/domain/openLink.ts`, `src/pendingJoin.ts`). The code survives the Google sign-in round trip for the session and is dropped from the address bar.
- WebMCP (`src/webmcp.ts`): in browsers that have `document.modelContext` (Chrome origin trial, https://developer.chrome.com/docs/ai/webmcp/imperative-api) the app offers nine tools to the browser's assistant: `log_baby_event` (one sentence, offline rules only; the parent sees "Assistant: Logged..." with Undo), `get_handoff_brief`, `get_today_summary` `get_upcoming_predictions` (next nap, feed and diaper check), `log_measurement` (kg and cm, same ranges as a measure entry, shown with Undo), `get_growth`, `get_milestones`, `get_vaccines` (the record and the CDC schedule lines for the age; read-only, and it does not say what is due) and `get_insights` (read-only; the insights are marked untrusted). There is deliberately no tool to answer a milestone: that is the parent's judgment. The Say it box is also a declarative-API tool (`fill_log_box`, https://developer.chrome.com/docs/ai/webmcp/declarative-api): no auto-submit, so the assistant fills the box and the parent presses Log it, which logs with the same rules and answers the assistant. Tools are not exposed to other origins (the default). Input is checked and capped at 500 characters; nothing happens in other browsers. The API may still change. Evals (`evals/webmcp/`, see `docs/PROCESS.md`): seventeen prompts with the tool call each should produce; the offline test passes, and the smoke run passed 8/8 before the growth tools were added and has not been repeated; the model-driven run (`npm run evals:webmcp`) has not been run yet, it needs an API key.
- Usage analytics, web only (`docs/PLAN_ANALYTICS.md`, `src/analytics.ts`): Google Tag Manager (with Google Analytics 4 inside it) loads only after a parent turns on Profile > Help improve Calendaby (off by default; the phone apps do not show it), and only the screen opened, the kind of entry logged and "invite shared" are handed to it, never text, names, dates, amounts or invite codes. The container still has to be set up in Tag Manager (steps in the plan) and checked in Google Analytics.
- Growth, milestones and insights (`docs/PLAN_GROWTH.md`, all phases built):
  - **Measurements.** A `measure` event (weight in grams, length and head in millimetres, any one or more) that syncs like every other entry. Logged from Log > Growth or typed ("weighed 6.2 kg, 62 cm, head 41 cm" is one entry; a unit is required and "in" must be "inch"), edited from the Timeline. Shown in lb/in or kg/cm to match the bottle unit setting. A read-only Growth card on Today shows the latest weight, length and head with their percentile; it opens the Growth & milestones screen (`src/ui/Growth.tsx`, `src/ui/Milestones.tsx`, switches `growth` and `milestones`).
  - **WHO percentiles.** Optional shared setting `babySex` (Profile > Baby). The WHO growth standards for 0 to 24 months (150 LMS rows from the CDC publication, generated by `scripts/make-growth-reference.mjs` into `src/domain/growthReference.ts`, planted into `growth_reference` by seed `growthRef-v1`, schema v11). Tests check the maths against published percentile columns. No sex, no birth date or over 24 months: no percentile. Deploy the server before the apps: an older server rejects the new `babySex` key.
  - **Milestones.** The CDC checklists from 2 months to 3 years (`src/knowledge/milestones.ts`, 10 ages, 4 areas, in the `milestone` table by seed `milestones-v1`, schema v12). The parent answers each item Yes, Not yet or Not sure; an answer is a `milestone` event, so it syncs between both parents, the latest answer counts and nothing is added to the server. "Not yet" items are listed under "Worth raising at the next checkup" with the CDC wording about acting early. Nothing is called a delay.
  - **Assistant tools (agentic RAG).** The chat agent has `getGrowth` and `getMilestones` (`growthReport`, `milestoneReport`) next to its other tools. They return only the baby's own readings and answers (sent in the request as `measures`, `marks`, `sex`, `birth`, so they do not depend on the latest 500 events) plus the WHO and CDC reference. There is no vector database: the corpus is small and structured and is looked up by age. `GUIDE_RULES` says percentiles are not a diagnosis and to point to the pediatrician for readings under the 3rd or over the 97th.
  - **Insights.** `/api/agent` has an `insights` mode: the model calls the same tools, then `publish_insights` with 1 to 4 cards. Sources are named by id and resolved server side, so a model cannot write a link; `sanitizeInsights` drops a card that is too long, has markup or a link, labels the baby (underweight, delayed, diagnoses), or is a growth, milestone or health card without a source. Cards are saved on the phone (`insight` table, schema v14, not shared) and drawn on Today (two newest) and on the Growth & milestones screen, with Got it. The app asks when it opens or comes to the front, at most every 6 hours and only if a measurement, milestone answer or checklist changed, or once a day otherwise (`src/domain/insights.ts`); it then shows one local notification (switches `aiInsights`, `alertInsights`). A server that is down is asked once per gap. Needs a birth date and the assistant reachable; it does not wake a closed app (there is still no server push). Because it runs on every phone that has the switch on, each parent's phone makes its own call.
  - **Not tried:** with a real model, on a phone, or with TalkBack. The browser tests (`e2e/growth.spec.ts`, `e2e/webmcp.spec.ts`) pass in Chrome; the assistant paths use a stub model in the tests.
- Vaccination record, phases 1 to 4 of `docs/PLAN_VACCINES.md` (Log > Vaccines, switch `vaccines`): a `vaccine` event (vaccine id and label, optional dose 1 to 5, place, lot and note) that syncs like every other entry, is shown and edited in the Timeline, and is refused if dated after today (checked when a parent logs or edits, not when an entry arrives from the other phone). The pick list is the `vaccine_type` table (schema v15, seed `vaccineTypes-v1` from the vaccines in `src/knowledge/checkups.ts`); a parent can add their own. The same dose of one vaccine logged twice within the duplicate window is refused. The Vaccines screen (a card on Today opens it; `src/ui/Vaccines.tsx`, `src/domain/vaccineRecord.ts`) lists the record newest first with edit, and beside it the visit at or before the baby's age and the next one from the CDC schedule in `checkups.ts`, each line showing how many doses of the vaccines it names are recorded or "not recorded yet" (a line naming two vaccines shows each; a custom vaccine appears only in the record), with the schedule's note and its CDC and MedlinePlus links; it never says due, late or missed. Without a birth date only the record shows. Visit prep (`visitPrep.ts`) adds a plan line naming the vaccines the visit lists that are already recorded, "the doctor decides what is due". The chat agent has `getVaccines` (`src/domain/vaccineReport.ts`): recorded doses (vaccine, dose, date) and the cited schedule lines for the age with dose counts; the chat prompt and the tool's `rules` forbid saying a dose is due, overdue, missed or up to date, or advising to give or skip one. Place, lot number and notes are stripped from every vaccine entry before any request to the agent (`withoutVaccineDetails`, chat and insights). The request has a `vaccines` field (up to 200) because the latest 500 events may not reach back to them. The WebMCP `get_vaccines` is built (phase 4); there is deliberately no tool to record a vaccination. The screens have not been tried on a phone or in the browser by hand; the tests cover the rules, the store, the schedule matching and a two-phone sync.
- Web guidance: front-end work starts with Chrome's `modern-web-guidance` skill (`.agents/skills/`, pinned in `skills-lock.json`; rule in `AGENTS.md` and `docs/PROCESS.md`). First pass, on the Vaccines screens: the calendar day shown to an assistant and the birth-date limit now use the parent's local day (`localDay` in `src/ui/time.ts`) instead of the UTC day, and the edit sheet's error is announced (`role="alert"`). Found and not yet done: the sheets are `div role="dialog"` with no Esc, focus containment or inert page (the guide says to use native `<dialog>` with `showModal()`), and about 85 font sizes in `src/App.css` are fixed `px`, so the OS text size and `<meta name="text-scale">` would not reach them. Temporal was not adopted: it is not in Safari yet and needs a polyfill dependency (rule 8).
- Sleep intelligence: the daily sleep goal can set itself (Profile > Quick picks & goals; on by default for a phone still on the starting 14 h). It takes the middle of the CDC range for the baby's age (14 to 17 h to about 4 months, so a newborn's goal is 15.5 h and can be above 15; 12 to 16 h to 1 year; 11 to 14 h to 3 years; table `sleep_need`, schema v13), then follows the baby's own last full days (at least 3, 4 h or more logged) inside that range (`src/domain/sleepGoal.ts`). Today shows where the number came from. Data errors in the sleep log are found and pointed at, not fixed (`src/domain/sleepIssues.ts`): two fell-asleeps with no wake-up, a wake-up with nothing before it (shown in the Timeline so it can be fixed), a stretch over 18 h, a sleep still open after 14 h, a finished day over 20 h. They show as a "Sleep log needs a look" card on Today and a warning on the Timeline entries. Notifications (switch `alertSleepCheck`): "still asleep?" after twice the usual nap (2 to 4 h) or 12 h at night, and one note per new data problem.
- Agent replies are formatted: the chat prompt asks for the answer first, key times in bold and at most four short bullets, and the Agent tab draws paragraphs, lists, bold text and https links (`src/domain/replyBlocks.ts`, `src/ui/Reply.tsx`). Only those elements are ever created; HTML and other link types from the model show as plain text.
- Accessibility (`docs/PLAN_ANDROID.md`): reduce-motion support, a Listen button that reads agent replies and the handoff aloud, "um" and "uh" removed from voice input, a skip link, a live region for chat replies, and a monochrome layer in the Android launcher icon. Not yet tried with TalkBack or the system font size on a phone.
- App icon and splash: sources in `assets/*.svg` (purple gradient, lilac crescent moon, green sparkle, matching the in-app logo); `node scripts/make-icons.mjs` renders every PWA, Android and iOS size through headless Edge or Chrome. `npm run android:install` also opens the app after installing.
- Husky pre-commit runs `npm run check` (lint, build, tests including a dev-server smoke test). A post-commit hook (`.husky/post-commit`) runs `npm run android:install` after every commit: it builds the debug APK and installs it if a phone is connected. It never fails the commit; skip it with `SKIP_ANDROID_INSTALL=1`.

## Run locally

Needs Node 22.13+. Copy `.env.example` to `.env.local`; set `OPEN_ROUTER_API` if it is not already an environment variable.

```bash
npm install
npx vite --host        # http://localhost:5173, API at /api/backend and /api/agent
npm run check          # lint, build, tests
npm run android:install  # build the debug APK; installs on a connected phone, skips the install if none
```

In PowerShell, `npm run dev -- --host` fails; use `npx vite --host`.

## Known gaps

- Sharing: baby name, birth date and tummy goal are not shared yet (phase 4); the assistant still uses the events the phone sends (phase 5). Preview and Production share one Turso database, and Preview has no `CLERK_SECRET_KEY`.
- The old backend SQLite (appointments, agent events) is a file on Vercel and does not persist; only the household log is in Turso.
- `/api/agent` is open unless `CLERK_SECRET_KEY` is set; set it on Vercel before going public.
- Activities and pumping are not in Analytics trends or the agent's `getPredictions` yet; the parser only knows the keywords for the four seeded activity types (a custom type is logged by tapping it).
- The rules parser misses some phrasings it doesn't flag as unclear ("about 60" without ml).
- Growth and sleep: the 18 h, 14 h and 20 h limits in `sleepIssues.ts`, the nap-check bounds in `notifications.ts` and the insight timing (6 h and 24 h) are still constants. The WHO percentiles stop at 24 months (CDC curves for older children are not included) and the baby's age is not corrected for prematurity. The milestone checklist wording is the CDC's, made gender-neutral; recheck `src/knowledge/milestones.ts` against the CDC pages before each release.
- Still hardcoded, to move into the database: night hours (7 pm to 7 am), nap wind-down lead (15 min), duplicate window (2 min), leave-for-visit lead (30 min), calendar margins, the prediction thresholds in `predictions.ts` and `outlook.ts`, the default theme section list, and the cited reference content in `src/knowledge/` (checkups, red flags, guidance). Server limits (invite lifetime, tries, batch sizes) stay as configuration. The caregiver fallback name "Parent" is still a literal.
